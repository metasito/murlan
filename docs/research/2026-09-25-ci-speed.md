# CI speed: where the time goes (#1285)

Measured 2026-09-25 from the GitHub API: 298 runs of `ci.yml` that had browser shards, from
2026-09-11 to 2026-09-25. In 256 of them every shard was green. Only green runs are priced here:
a spec that fails at its timeout reads as its timeout, and one that fails on its first assertion
reads as a few seconds.

## Mechanisms, measured

- **mockupParity was one file.** Its tests took 162–168 s (trick on Skia), 120 s (trick on the
  fallback), 54 and 37 s (rest), 47 s (score-open), and 10 and 6 s (felt loading). It is now four
  files, one per heavy moment.
- **What one parity step costs** (mockup side, local, 120 steps):
  - `clock.runFor`: 29 ms
  - the animation nudge: 15.5 ms
  - the sample: 2 ms
  - a screenshot: 63–90 ms
  - a JPEG decode: 8 ms
  - `recorded()` copied the whole growing trace out of the page on every step. That is O(n²) over
    the window.
  - Raw CDP `Page.captureScreenshot` at `scale: 2` produces the same bytes as `page.screenshot`
    (40 of 40 frames, offset clip included) in 60–66 ms instead of 90–108 ms.
  - The trick moment has no regions, yet it decoded every frame anyway.
- **score-open did not replay.** `Animation.setPlaybackRate(0)` was sent after load. By then the
  mockup's `#turn` transition (`border-color .2s …`) had run for 150–193 ms of real time. Sending
  it before navigation took 8 local runs from 3 distinct first frames down to 1. The ticket's first
  guess, that animations run in real time between steps, is refuted: once frozen, the timeline
  holds.
- **feltParityGrid** reloads the app for each of its 12 cells, waits a fixed 2 s for the deal,
  then waits for the Skia felt. Phone takes 78–84 s and tablet 138–162 s. The jump to 216–246 s
  arrived with #1278 (the Skia one-lamp rig). The file is now split per viewport.
- **tapTargets** jumped on 09-21. One online-hand test accounts for 78–90 s of it. That test was
  not isolated further here. At 157 s the spec is under the fair share, so it does not block the
  split.
- **The hung `npm test`** (run 36113803629) had two causes:
  - `passwordReset.test.ts` ran `reset-password.mjs` through `execFileSync`. Register replies 202
    and only then mints its code, inside a transaction that holds the user's row
    (`FOR NO KEY UPDATE`). The script's `UPDATE users` waited on that lock. The lock could only be
    released by the event loop of the in-process test server, which `execFileSync` was blocking.
  - `--test-timeout` cannot fire in a blocked loop, and neither can `--test-force-exit`. This was
    measured: a synchronous child and a never-settling top-level await both outlived them.

## Options, cost and gain

| option | cost | gain | taken |
|---|---|---|---|
| Split the files over the fair share (mockupParity ×4, feltParityGrid ×2) | 2 helper modules | removes the 443 s floor | yes |
| Take the shard count from the timings: `ceil(total / (300 − 90))`, capped at 12 | a scope step, one output | the slowest shard tracks the target as the suite grows | yes |
| Price by the latest green run: this branch's artifact, then main's, then the committed file | a 90-day artifact, one API call | no commit to main per merge, and a branch that makes a spec heavier is split by its own numbers | yes |
| Metro transform cache across runs | one `actions/cache` step | `expo export` 55 s cold, 7 s warm (local) | yes |
| `dev-stack up` in parallel with the export | a few lines in `scripts/e2e-server.mjs` | 10–20 s per shard | yes |
| CDP capture, frame lookup inside the page, no decode without regions | helper changes | about 40% of a parity step | yes |
| A per-file deadline for `npm test` (a worker thread's timer, then SIGKILL) | a preload | a hang fails in 150 s, naming its file, instead of burning the job's 20 min | yes |
| Raise `npm test` concurrency | none | unmeasured: the integration files share one Postgres | no, until measured |
| Build the bundle once and share it with the shards | one job the shards wait on | loses: measured on run 33063120496 (see `ci.yml`) | no |
| Playwright's own `--shard` with `fullyParallel` | none | splits by test count, and these tests range from under 1 s to 168 s | no |

The cap of 12 exists because GitHub's Free plan runs 20 concurrent jobs, and those 20 are shared
by every run in the repository. `tests/tooling/e2eShardSplit.test.ts` fails if the suite needs
more than 12 shards to meet the target.

## Shard balance: why one or two shards finished light

Six green runs after #1289 were measured: 36138538626 and 36140927385 (12 shards), and 36144919404,
36164927382, 36168584868 and 36171489488 (11 shards). For each, the plan was recomputed with
`assignShards` from that run's own `timings=` line (the scope job's log), then compared per shard
with the real `Browser tests` step. The plans were flat (161–162 s a shard on 36138538626). The
real steps were not.

| run | spread (max−min)/min | light shard: predicted → real | why |
|---|---|---|---|
| 36138538626 | 73% | 1: 161 → 110 s; 12: 162 → 128 s | `mockupParityTrickLandingsSkia` priced 145 s, ran 78 s; `pileHandoff` unmeasured at 60 s, ran 3 s |
| 36140927385 | 88% | 12: 162 → 128 s | the same plan and prices |
| 36144919404 | 102% | 3: 155 → 108 s | `resultActions` priced 93 s, ran 26 s |
| 36164927382 | 116% | 3: 166 → 103 s | `resultActions` priced 91 s, ran 26 s |
| 36168584868 | 40% | none light | `resultActions` back at 26 s |
| 36171489488 | 31% | none light | the same |

**The cause is the price, not the packing.** A spec is priced from the single latest green run
that measured it. The two specs behind the light shards vary a lot from run to run, on one
attempt each (no retry, and the flaky gate was silent):

- `resultActions.spec.ts` plays a whole bot-driven match. It was priced at 93 s from main's run
  36140927385, and at 91 s from one 1.5 min attempt in run 36164141171. It ran 26 s on the runs
  planned from those prices. Its committed price has moved 55.9 → 29.7 → 46.4 → 40.5 s.
- `mockupParityTrickLandingsSkia.spec.ts` was priced at 145 s from one attempt of 2.0 min in run
  36140927385, and ran 78 s on the next.

An unmeasured spec at `UNMEASURED_SECONDS` is the same error once, until its first green run
prices it (`pileHandoff.spec.ts`: 60 s against a real 3 s).

**Not the cause:** a per-file cost. Fitting real − predicted ≈ k·files + c over 68 shard
observations gives k = 6.3 s/file and a residual of 26.1 s against a raw 26.5 s, so file count
explains almost nothing.

**20% is out of reach by packing alone.** On the shards holding neither spec, real exceeds
predicted by a mean of 17 s with a standard deviation of 21 s. The spread is about 3 × 21 s over a
floor near 150 s, so 30–40%, which is what the two runs that drew no bad price show (31%, 40%).
No packing of fixed prices can do better than the specs' own variance, and the slowest job is
already within 5 min on every run measured. The ways on, for the owner to choose:

1. **Accept 30–40%.** The 5-minute target the ticket was opened for holds.
2. **Price from several runs.** Take each spec's median over the last few main artifacts rather
   than the latest one. This removes the 70–116% spikes a single outlier causes, not the 30–40% floor.
3. **Steady the two specs.** Make `resultActions`' match deterministic, and bound the Skia parity
   capture. This attacks the floor, but it is test work outside the splitter.

## Shard balance: what the fixes did (PR #1312)

Five changes, each aimed at a measured source of spread:

- **Median pricing.** Main's specs are priced at the median of its last five green runs.
- **Seeded deals.** `resultActions` and `resultCutout` now play a seeded hand. Each plays a hand only to reach a screen that is measured. Across the eight green runs above, `resultCutout` was the noisiest spec (23–84 s, σ 23 s over the six runs whose log tail held all of it). `resultActions` ran 26–37 s over four.
- **Local CanvasKit.** The Skia parity specs load CanvasKit from `node_modules` instead of the CDN.
- **Side-by-side capture.** A parity test captures its app and mockup sides at the same time.
- **A phase line.** Each parity test prints how long each phase took.

| run | shards | `Browser tests` step, s | spread | slowest job | whole run |
|---|---|---|---|---|---|
| 36194158965 | 12 | 128–189 | 48% | 221 s | 4.5 min |
| 36194716344 | 11 | 149–222 | 49% | 247 s | 5.1 min |
| 36197381644 | 11 | 149–199 | 34% | 223 s | 4.7 min |
| 36198833114 (2nd attempt) | 11 | 142–211 | 49% | 232 s | 4.9 min |

The 73–116% spikes, where a single sample mispriced a spec, did not recur. What remains is the
floor below, measured against eight earlier runs' per-test times:

- **Setup is not the cause.** Setup inside the step is 0–6 s on every shard. The spread is test time.
- **The runners are steady.** Quiet specs deviate from their own mean by 2.5%. The noise belongs to a few specs.
- **Parity specs are CPU-bound.** Profiled locally, a trick moment's mockup side is 63 s: 426 clock
  steps at 93 ms, almost all of it waiting on the browser to render the scene at DPR 2 (the
  in-page work is 0 ms), and 213 screenshots at 104 ms. Running the sides together cut the Skia trick
  test from 2.1 to 1.4 min. The fallback trick test barely moved, because its mockup side slows
  under the shared CPU.
- **Random games stay random.** `offline`, `offlineFour`, `offlineMatch` and the online specs play
  deals that are random on purpose (the online ones on the server). That is what they check, so they
  keep their 5–15 s swings.

**Net effect.** The spikes are gone, and the typical run is better. The six runs before this PR
averaged a 75% spread, four of them at 73–116%. The four after it average 45%, and none spiked. The
floor did not move: 34–49% after, against 31% and 40% on the two earlier runs that drew no bad price.
Total time did not drop either. Summed shard time went from 2001 s (36197381644) to 1941 s
(36198833114): running the sides together sped the Skia trick test up, but contention gave most of
it back elsewhere. The whole run stays at 4.5–5 min.

With about 11 shards of 165 s and items varying by 15–20 s, static sharding settles near 35–50%.
That is an estimate: LPT over each spec's mean and σ from those eight runs, 3000 drawn runs, and it
was not shipped. It also found that pricing noisy specs above their median does not help (32–38%).
Reaching 20% needs shards that take specs from a shared queue as they finish, not fixed lists.

## Sources

- Playwright sharding: <https://playwright.dev/docs/test-sharding>. `--shard` assigns whole files
  unless `fullyParallel` is on.
- Node test runner: <https://nodejs.org/api/test.html>. Each file runs in its own child process,
  and `--test-timeout` applies per test.
- Jest `--shard`: <https://jestjs.io/docs/cli#--shardshardindexshardcount>. It also splits by file,
  so it would not balance a heavy file either.
- GitHub Actions:
  - Artifacts REST API: <https://docs.github.com/en/rest/actions/artifacts>. It lists artifacts by
    `name`, with `expired` and `workflow_run.head_branch` / `head_repository_id`.
  - Limits: <https://docs.github.com/en/actions/reference/limits>. The Free plan allows 20
    concurrent jobs, and a matrix allows 256 jobs per run.
