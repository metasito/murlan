Measured 2026-09-25 from the GitHub API: 298 runs of `ci.yml` that had browser shards, from
2026-09-11 to 2026-09-25. In 256 of them every shard was green. Only green runs are priced here:
a spec that fails at its timeout reads as its timeout, and one that fails on its first assertion
reads as a few seconds.

Over the same window the suite went from 1111 s to 2118 s. Playwright assigns a whole file to one
shard, so a 443 s file sets a floor of 443 s plus setup on the slowest shard, however many shards
there are.

## Mechanisms, measured

- **mockupParity was one file.** Its tests took 162–168 s (trick on Skia), 120 s (trick on the
  fallback), 54 and 37 s (rest), 47 s (score-open), and 10 and 6 s (felt loading). It is now four
  files, one per heavy moment.
- **What one parity step costs** (mockup side, local, 120 steps):
  - `clock.runFor`: 29 ms
  - the animation nudge: 15.5 ms
  - the sample: 2 ms
  - a screenshot: 63–90 ms
  - a JPEG decode: 8 ms
  - `recorded()` copied the whole growing trace out of the page on every step. That is O(n²) over
    the window.
  - Raw CDP `Page.captureScreenshot` at `scale: 2` produces the same bytes as `page.screenshot`
    (40 of 40 frames, offset clip included) in 60–66 ms instead of 90–108 ms.
  - The trick moment has no regions, yet it decoded every frame anyway.
- **score-open did not replay.** `Animation.setPlaybackRate(0)` was sent after load. By then the
  mockup's `#turn` transition (`border-color .2s …`) had run for 150–193 ms of real time. Sending
  it before navigation took 8 local runs from 3 distinct first frames down to 1. The ticket's first
  guess, that animations run in real time between steps, is refuted: once frozen, the timeline
  holds.
- **feltParityGrid** reloads the app for each of its 12 cells, waits a fixed 2 s for the deal,
  then waits for the Skia felt. Phone takes 78–84 s and tablet 138–162 s. The jump to 216–246 s
  arrived with #1278 (the Skia one-lamp rig). The file is now split per viewport.
- **tapTargets** jumped on 09-21. One online-hand test accounts for 78–90 s of it. That test was
  not isolated further here. At 157 s the spec is under the fair share, so it does not block the
  split.
- **The hung `npm test`** (run 36113803629) had two causes:
  - `passwordReset.test.ts` ran `reset-password.mjs` through `execFileSync`. Register replies 202
    and only then mints its code, inside a transaction that holds the user's row
    (`FOR NO KEY UPDATE`). The script's `UPDATE users` waited on that lock. The lock could only be
    released by the event loop of the in-process test server, which `execFileSync` was blocking.
  - `--test-timeout` cannot fire in a blocked loop, and neither can `--test-force-exit`. This was
    measured: a synchronous child and a never-settling top-level await both outlived them.

## Options, cost and gain

| option | cost | gain | taken |
|---|---|---|---|
| Split the files over the fair share (mockupParity ×4, feltParityGrid ×2) | 2 helper modules | removes the 443 s floor | yes |
| Take the shard count from the timings: `ceil(total / (300 − 90))`, capped at 12 | a scope step, one output | the slowest shard tracks the target as the suite grows | yes |
| Price by the latest green run: this branch's artifact, then main's, then the committed file | a 90-day artifact, one API call | no commit to main per merge, and a branch that makes a spec heavier is split by its own numbers | yes |
| Metro transform cache across runs | one `actions/cache` step | `expo export` 55 s cold, 7 s warm (local) | yes |
| `dev-stack up` in parallel with the export | a few lines in `scripts/e2e-server.mjs` | 10–20 s per shard | yes |
| CDP capture, frame lookup inside the page, no decode without regions | helper changes | about 40% of a parity step | yes |
| A per-file deadline for `npm test` (a worker thread's timer, then SIGKILL) | a preload | a hang fails in 150 s, naming its file, instead of burning the job's 20 min | yes |
| Raise `npm test` concurrency | none | unmeasured: the integration files share one Postgres | no, until measured |
| Build the bundle once and share it with the shards | one job the shards wait on | loses: measured on run 33063120496 (see `ci.yml`) | no |
| Playwright's own `--shard` with `fullyParallel` | none | splits by test count, and these tests range from under 1 s to 168 s | no |

The cap of 12 exists because GitHub's Free plan runs 20 concurrent jobs, and those 20 are shared
by every run in the repository. `tests/tooling/e2eShardSplit.test.ts` fails if the suite needs
more than 12 shards to meet the target.

score-open replayed byte for byte with no retry.

## Sources

- Playwright sharding: <https://playwright.dev/docs/test-sharding>. `--shard` assigns whole files
  unless `fullyParallel` is on.
- Node test runner: <https://nodejs.org/api/test.html>. Each file runs in its own child process,
  and `--test-timeout` applies per test.
- Jest `--shard`: <https://jestjs.io/docs/cli#--shardshardindexshardcount>. It also splits by file,
  so it would not balance a heavy file either.
- GitHub Actions:
  - Artifacts REST API: <https://docs.github.com/en/rest/actions/artifacts>. It lists artifacts by
    `name`, with `expired` and `workflow_run.head_branch` / `head_repository_id`.
  - Limits: <https://docs.github.com/en/actions/reference/limits>. The Free plan allows 20
    concurrent jobs, and a matrix allows 256 jobs per run.
