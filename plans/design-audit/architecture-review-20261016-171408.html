Problem. "Who acts next, after how long a hold, against what deadline" is decided twice: armTurn on the server and the bot loop CLI-6 moves unchanged into offlineDriver. The two already differ. Offline gives no deadline on a lead and pauses the clock during the opening; online arms a deadline on every turn and adds Reading.notice on the server, a UI token the server imports. GAME-RULES § Decisions "The offline turn clock" records that this drifted once (20 s against 30 s). CLAUDE.md's autoMove invariant covers which move a bot makes. Nothing covers when it makes it.

Solution. A pure turn-schedule module beside autoMove. It takes a state and its lastMove and returns the acting seat's kind, the hold before it may act, and its deadline policy. The server's timers and the offline driver become its two adapters. Screens stop passing includeNewTrick and pausable, and the hold durations the server reads from lib/timeline and lib/tokens move behind the module's interface.

  • Locality: every turn-timing bug in one module
  • Leverage: one interface, server and offline
  • Tests: a node table per lastMove kind
  • The server stops importing UI tokens
  • Mode differences become named, not accidental
Whether a lead is timed offline is a rule. Keep today's per-mode answers as explicit policy rows, and change one only through a GAME-RULES § Decisions entry.

Before: one GameState change, three hand bumps

PROTOCOL_VERSION: hash-guarded (WIRE-1)
GAME_SCHEMA_VERSION: bumped by hand
OFFLINE_SAVE_VERSION: bumped by hand
offlineSave.v<N>.json: new fixture each time

Five WIRE tickets each say "schema +1, offline +1". R1 notes WIRE-5's design left out the offline bump.

After

GameState codec

parse, encode, shape fingerprint pinned like the protocol hash

wire
embeds it
server envelope
own fields + shape
offline save
own fields + shape

An envelope's own version moves only when the envelope's own fields change.

Problem. WIRE-3 gives a stored GameState one parser. Whether a stored blob is still safe is held by two hand-bumped integers that every shape ticket must remember. Engine design §9 settles it as "whoever lands second bumps again". A missed bump is the failure both version comments warn about: a silently corrupt restore.

Solution. The gameStateSchema module also owns the stored shape's identity: a fingerprint pinned by the same kind of test as the protocol hash. The server envelope and the offline save each record that fingerprint beside their own version, and refuse a mismatch the way they refuse a version mismatch today.

  • Interface shrinks: no lockstep constants
  • Locality: shape change, one module
  • Leverage: five WIRE tickets, zero manual bumps
  • Tests: one pin replaces vigilance
  • R1's bump count unchanged

3. The live table holds ledgers, not twenty writable fields

Worth exploring in-process builds on SRV-6, SRV-3, SRV-4, ENG-1, ENG-4

  • server/game/matchLedger.ts (SRV-6)

  • tests/server/seatLedger.test.ts (scan)

Before: mass of OnlineGameState

interface ~20 mutable fields
ledgers seat + match
Single writer held by two source scans with self-tests (SRV-6), not by the type

After

interface round, seats, match
ledgers own their fields, pack themselves

Problem. After SRV-6, matchLedger and seatLedger are the only writers, but OnlineGameState still exposes every field as writable. Two scans enforce ownership. Memory "a source scan falls to a decoy" applies: an alias or destructure has already needed a scan fix (c8fb9e5e).

Solution. The live table holds a seat ledger, a match ledger and the round. Each owns its fields behind a read-only view, and each packs and unpacks its own block of the envelope, which already has match and seats blocks. The scans become a type error and are deleted.

  • Single writer by construction
  • Delete fieldWrites scans
  • Envelope blocks map one-to-one
  • Tests hit ledger interfaces
Do not stretch this into one match record shared with offline matchFlow. Engine design §3.3 rejected that, for server keying. It is a plan decision, not an ADR, and the friction here does not need it.

Problem. ENG-6 makes Move the engine's input, and the server takes it through one moveAction. The wire, both providers and GameTable's props still say play / pass / give as three separate paths. A new move kind, a rate rule or a refusal therefore touches the protocol, three registrations and both providers.

Solution. The Move union crosses the socket as one intent, and GameTable and both providers expose one act(move). Ride an R1 bump that is already planned (for example WIRE-1), so the bump count does not grow.

  • Leverage: Move type, end to end
  • Recorded moves replay on either table
  • FakeSocket asserts one event
  • GameTable interface narrows

Problem. lib/captureStates.ts is production code, so it cannot use TEST-1's state(). It builds GameState literals by hand, which is why WIRE-1 and WIRE-4 both list it. state(over) still lets a test build a state no deal reaches, with a lastMove that disagrees with the table. That is the state WIRE-3's parser refuses and ENG-7 says cannot arise.

Solution. A pure, production-safe situations module. Each named situation is a fixed deal plus a script of moves, reached through startRound and applyMove. Captures, the e2e opener, bench scenarios, TEST-8 presets and node fixtures all name a situation. Each test fixture then carries a valid lastMove and demand.

  • Shape tickets edit no fixtures
  • Fixtures pass parseGameState by construction
  • Capture and web runs share states
  • Delete the re-deal loop

Problem. ENG-2 makes the GIOCA label read the engine's code. The server still maps five distinct codes onto INVALID_MOVE, so the same refusal reads "too low" on the button and "Invalid move" in the float. The tutorial keeps a third map.

Solution. The wire carries the engine's refusal code with its params. One client wording table keyed by MoveRefusal serves GIOCA, the server float and the tutorial's overrides.

  • One wording per refusal
  • Delete the lossy server map
  • i18n ratchet keys on engine codes

Speculative because GIOCA already blocks most illegal plays, so the server float is rarely seen.

Top recommendation

1. One turn schedule for both tables

"When may this seat act" is the same kind of bug as CLAUDE.md's autoMove invariant. It has drifted once already (the GAME-RULES offline clock), still differs between online and offline, and caused the latest hot spots (#1624, #1638, #1639). CLI-6 moves it unchanged, so the plan would leave two copies. Schedule it after CLI-6, ENG-7, WIRE-2 and TIME-1, so that it keys on lastMove and arms through the one server clock.
