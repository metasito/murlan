Murlan Redesign Programme

234 verified findings from a full audit of the codebase. Instead of 234 patches, the proposal is eleven redesigns plus a handful of small fixes, sequenced into 73 tickets that the queue loop can work one at a time.

Status: proposal. Nothing has been filed. Tickets are created only after the owner approves, through /mattpocock-skills:to-tickets.

The one pattern

Why redesign instead of patch

Most findings share one cause. A module offers the raw steps but not the decision, so each caller works out the decision itself: the server, the offline game, the tests and the screens each re-derive "is the match over", "whose turn is it", "what just happened" or "may this table be released". The bugs in the audit are mostly two of those copies disagreeing.

Each redesign makes the same move: give one decision one owner, make every caller ask it, delete the copies. "Better" is measured three ways: a fix lands in one place (locality), callers learn less (leverage), and tests run the real code instead of a copy or a mock (testability).

Where nothing structural is wrong, the fix stays a small fix. The hygiene and native tickets are those.

Reviewer notes

Risks I checked, and what remains

  • No silent rule changes. Two engine tickets touch game behaviour: ENG-7 deletes the stuck-exchange valve and ENG-6 makes the engine refuse a move out of turn. GAME-RULES § Decisions makes an empty giveback set reachable only from an empty hand, which a real deal never produces, and the server already refuses NOT_YOUR_TURN. Both are listed as D1 and D2 rather than assumed.
  • No regressions by construction. Every behaviour-changing ticket starts with a test that is red on today's code; every move-only ticket starts with a pin that is green on today's code and must stay green after. Ticket pairs that touch the same file are ordered by blocked-by edges, checked mechanically (no unordered pair, no cycle).
  • Owner-eye tickets and the loop. Six tickets change something visible (UI-3, UI-6, UI-7, UI-8, UI-9, CLI-7). The plan asks for captures and a PR left for the owner, but the loop merges automatically once CI is green and the review lands. Either label those six ready-for-human, or accept reviewing them after merge. This is D27.
  • The wire changes five times. Each change to shared/protocol.ts needs its own version bump, which the protocol test pins. Five bumps and two minimum-version raises are fine before launch, but each needs the server deployed first and a fresh tester build (D5).
  • The loop edits itself. Ten tickets change tools/loop while it runs. From LOOP-3 on, a read-only queue-loop.mjs --check runs the real wiring before each loop change lands, and every move keeps the entry path and exit code fixed.
  • It is long. The longest blocked-by chain is 25 tickets, and the loop takes one at a time. The waves show what can start immediately; wave 0 has eleven independent tickets.
  • One redesign skipped. L-107 (joker rank size) needs the owner's eye and is left as D13, not built.
